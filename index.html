    How merge sort works

    Merge sort is the standard example of divide and conquer: break the problem into smaller copies of itself, solve those, then combine the answers.

    Divide

    Find the middle with mid = ⌊(lo + hi) / 2⌋ and split the range into two halves. This costs Θ(1).

    Conquer

    Sort each half by calling merge sort on it. A range of one element is already sorted, which stops the recursion. This is the 2T(n/2) term.

    Combine

    Merge the two sorted halves by repeatedly taking the smaller front element. One pass over n elements, so Θ(n).

    Why it costs Θ(n log n)

    Every level of the recursion tree handles all n elements once, and halving the size each time gives log₂ n levels below the root. The grid below shows n = 16.

    T(n) = 2T(n/2) + cn = cn per level × (log₂ n + 1) levels = Θ(n log n)

    Master theorem check: a = 2, b = 2, f(n) = Θ(n) = Θ(n^(log_b a)). That is case 2, so T(n) = Θ(n log n).

    Why the merge is correct

    The merge keeps one invariant: after k steps, the output holds the k smallest elements of both halves, in sorted order. Because each half is sorted, the smallest remaining element is always at the front of one of them, so comparing just two elements is enough.

    When one half runs out, everything left in the other half is larger than all output so far and already in order, so it is copied across with no more comparisons.

    Taking the left element when the two are equal (L[i] ≤ R[j]) keeps equal values in their original order. That is what makes the sort stable.

    Merging halves of sizes m and n takes at most m + n − 1 comparisons.

    Common viva questions

    Short answers you can build on. Open each one.

    Why is merge sort Θ(n log n) even in the best case?
    The splits do not depend on the data: the array is always halved, giving about log₂ n levels. Each level merges n elements in total, so the work per level is Θ(n) whatever the input order. Sorted input only makes each merge cheaper by a constant factor, since it needs about half as many comparisons.
    Is merge sort stable, and why?
    Yes. During a merge, when the front elements of the two halves are equal, the algorithm takes the left one first. Equal elements therefore keep their original relative order. Using strict < instead of ≤ would break stability.
    What is the space complexity?
    Θ(n) auxiliary space for the temporary arrays used while merging, plus O(log n) for the recursion stack. This is the main drawback compared with in-place sorts such as heap sort.
    Merge sort or quick sort?
    Merge sort guarantees Θ(n log n) and is stable, but needs Θ(n) extra space. Quick sort sorts in place with O(log n) stack space and is often faster in practice, but its worst case is Θ(n²) and it is not stable.
    Can merge sort be written without recursion?
    Yes. Bottom-up merge sort treats every element as a sorted run of length 1, then merges neighbouring runs into runs of 2, 4, 8 and so on until one run remains. It performs the same merges without a call stack.
    When is merge sort the better choice?
    When stability matters, when worst-case guarantees matter, when sorting linked lists (merging needs no random access and can relink nodes), and for external sorting of data too large for memory, because merging reads its inputs sequentially.
    What is the worst-case number of comparisons?
    For top-down merge sort it is n⌈log₂ n⌉ − 2^⌈log₂ n⌉ + 1. For n = 8 that is 8·3 − 8 + 1 = 17. The Analysis tab measures this against real runs.
